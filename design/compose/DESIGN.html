BillOwl · Design Document · Compose (photo + caption, one send)

Pin a note to the photo — send them as one bill

A compose affordance for the Record input bar: pick a receipt photo, then attach a caption (typed or dictated) to that photo, and send both together as one input — so Ollie reads the picture and your sentence as a single bill and the caption fills the photo's gaps (a cut-off total, an unreadable date). This is the user-directed complement to F5's agent-proposed fusion: here you say "these belong together," so the agent never has to guess. · v1 · 2026-06-22 · sits beside the F5 Done-adding → untangle flow, doesn't replace it

1 · The problem, precisely

A receipt photo often doesn't carry everything: the total is cut off, the print is faded, the date is unreadable, or it's a group meal and only you know the split. Today the input bar's PhotosPicker calls loadPhotos → coordinator.submitPhotos the instant a photo is picked — the photo is recognised alone, and any sentence you type to fix it (send → submitText) becomes a second, separate card. The agent then has to infer that the photo and the sentence are the same bill. That inference is exactly what F5's Done adding → untangle → fuse flow does — agent-proposed, and only as good as the guess.

Compose removes the guess. The user attaches the sentence to the photo before sending, so the photo and caption arrive as one recognition input and the caption authoritatively fills the photo's gaps.

Two flows, deliberately coexisting. Compose = the user explicitly bundles a photo + caption up front (no guessing). F5 fuse = the agent finds un-bundled inputs that look like one bill, and proposes a merge to confirm. Compose narrows what F5 ever has to reason about; it never replaces it. A user can still drop loose photos and notes and let Ollie untangle them — that path is byte-for-byte unchanged.

2 · The compose interaction

The chosen model is a staged-photo chip with an inline caption, sitting in a tray directly above the existing input bar. Picking a photo no longer submits — it stages. The field you already have becomes the caption for the staged photo, and the existing send button (arrow.up.circle.fill) sends the photo + caption as one.

1Pick → stage, don't submit

Tapping 📷 and choosing a receipt parks it as a thumbnail chip in a tray above the field. The bar grows upward to hold the tray; the layout below is untouched. Behaviour change: loadPhotos stages into compose state instead of calling submitPhotos.

2The field is now the caption

The placeholder swaps to Add a note for this photo…. Whatever you type rides with the staged photo, not as its own card. Empty caption is allowed — you can still send a photo with no note (same as a plain photo-only capture).

3🎤 dictates into the caption

The mic now feeds the caption for the staged photo, mirroring the live transcript into the field (the existing voice.transcript binding) instead of submitting on its own. Stop → the transcript stays as the editable caption; you tap send when ready.

4One send → one bill

The send button sends photo + caption together. The bar returns to its empty resting state. One agent card appears, its fields drawn from both the picture and the caption.

Why a chip-and-caption tray, not a separate compose screen. The receipt-fixing moment is small and impatient — the user is staring at a photo with a missing total and wants to add one sentence. A chip that grows the existing bar keeps them in the same place, reuses the field + mic + send they already know, and reads as "this note belongs to this photo" at a glance. A full-screen composer would be heavier than the job.

3 · Multiple photos — each chip gets its own caption

Recommendation: per-chip captions, not one caption for the batch. The picker already allows up to 10 photos. If the user stages several, each appears as its own chip in the tray, and the caption field binds to the active (selected) chip — tap a chip to make it active, then type/dictate its note. Send dispatches one request per chip (photo + that chip's caption), producing one bill each.

Why per-chip beats one shared caption. The whole point is to fix a specific photo's gap — "this hotel receipt's total is ¥1,820," "that taxi one is the ¥48 ride." A single caption smeared across three receipts would be ambiguous and re-introduce the very guessing compose exists to remove. Per-chip keeps each note authoritative for exactly one bill. A chip with no caption simply sends photo-only (unchanged). For the common case — one photo, one note — this collapses to the simplest possible interaction with zero extra taps.

The active chip is shown with a terra ring; others sit muted. A small caption preview line under each chip ("¥240 · the total") reassures the user which note is pinned to which photo before they send.

7 · Voice caption — device-only

The mic dictates straight into the staged photo's caption: the existing live-transcript binding (voice.transcript → field) now targets the caption rather than a standalone submit. On stop, the transcript stays as the editable caption — the user reviews it and taps send when ready (no auto-submit, so a misheard amount can be fixed first).

Simulator has no microphone. VoiceCapture.beginSession already hard-fails on the Simulator ("Voice input needs a real device — the Simulator has no microphone."). Voice captioning is therefore device-only; on the Simulator the chip + typed caption path is fully testable, but the 🎤 path must be verified on hardware. Flagging this so QA screenshots of the voice-caption state come from a device, not the Simulator.

8 · Server-contract dependency (for Tech)

Recognition must accept an image and accompanying text in the same request. Today APICaptureRequest (BillMind/Services/AIService.swift:255) carries both text and imageBase64 as optionals, but the two client paths only ever set one: submitText sends text with imageBase64: nil (RecordCoordinator.swift:140), and extract(image:) sends imageBase64 with text: nil (RecordCoordinator.swift:225). The server's /v1/recognition endpoint correspondingly treats it as an EITHER/OR. Compose needs the server to read photo + caption together — vision OCR plus the caption as authoritative gap-fill (the caption supplies the total/date/who when the image can't), returning one card. The client change is small (a new submitComposed(image:caption:) that populates both fields in one APICaptureRequest); the load-bearing change is server-side: the recognition prompt/handler must accept and jointly reason over image + text, with the caption taking precedence for a stated amount over an unreadable one — and never inventing money if neither yields a total.

No new endpoint is required if /v1/recognition simply stops assuming exclusivity and handles the both-present case. F5's untangle endpoint is untouched — compose pre-bundles, so there's nothing for untangle to fuse.

9 · What must NOT change

  • Text-only path: type → send → submitText. Byte-for-byte unchanged when no photo is staged.
  • Photo-only path: staging a photo and sending with an empty caption recognises the photo alone — same result as today's instant submit, just one tap later.
  • F5 Done-adding → untangle → fuse: still available for loose, un-bundled inputs. Compose reduces how often it's needed but never disables it.
  • The money rule: one bill per composed send; amount never invented; "amount required" still gates Save.

10 · Open question + assumption

Ambiguity: the brief says "pick the photo, then add a caption." With multiple staged photos, must the user caption each before sending, or can they send a mixed batch (some captioned, some not)? Assumption (documented above): mixed batches are allowed — each chip sends with whatever caption it has (including none), one bill per chip. This keeps the common one-photo case trivial and never forces busywork on a batch where only one receipt was actually broken. If the PM wants a stricter "caption everything first" gate, that's a small follow-up on the send guard.
