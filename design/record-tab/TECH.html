Record Tab

A capture surface that turns a typed phrase (v1 primary) or a photo into a confirmed bill in a chosen journal, driven by the verified RecordingSession agent core.

branch feat/recording-agent-foundation (stacked on PR #3) gates Reviewer → you → Reviewer(E2E) → Manager schema unchanged

1Goal & non-goals

Goal: Give the agent core a real screen. The user types something like ramen 2840, the agent forms an editable bill card, asks at most a couple of chip-answerable questions when a field is unclear, and writes a BillRecord only when the user confirms. Additive — existing manual / import / Minds flows are untouched.

v1 IN scope

  • New Record tab
  • Text capture: local, deterministic parse (no network / API key) → draft
  • Photo capture: PhotosPicker → AIService.recognizeBill (demo mode works with no key)
  • Full agent loop: validate → clarify (chips) → review → confirm
  • Editable cards: tap-to-edit amount / merchant / date / category; skip + acknowledge
  • Confirm → persist: one BillRecord into the selected journal
  • Journal selector; graceful "no journals yet" state

v1 OUT (follow-ups)

  • Real multi-provider structured-output mode (validate is the backstop)
  • Voice capture; image downscaling at intake; streaming-animation polish
  • sourceSessionID + audit blob (needs SchemaV2 — kept out to leave the schema unchanged)
  • Replacing the Minds tab; conversational (LLM) repair

2Information architecture

Add Record as the 2nd tab in ContentView: Journals · Record · Statistics · Minds · Settings (5 tabs).

  • Rationale: additive and non-destructive. The earlier "talk to record" concept made Record central and folded Minds into journals, but that removes a shipped feature and is out of scope for v1. A 5th tab is acceptable on iPhone and keeps the change reviewable.
  • Tab icon: text.bubble; tint SketchTheme.dustyRose.

Core addition (agent core, with unit test)

RecordingSession.edit(cardID:field:value:) — applies a direct field edit (tap-to-edit on a card), pins the field, and re-resolves the card (same machinery as answer, but not tied to an open clarify question). This is what makes a blocked/flagged card recoverable by editing rather than only by chip.

One-line validator change: the missing-date gap lists Today and Yesterday as its chip options — Yesterday via a guard let on Calendar.current.date(byAdding: .day, value: -1, to: today) (not a force-unwrap, matching the file's style). Everything else for date/category correction is a UI affordance that calls answer/edit with an arbitrary value — no further core change.

The coordinator (the "session actor")

@MainActor @Observable
final class RecordingCoordinator {
    private(set) var session: RecordingSession   // pure value-type core
    let journal: Journal
    private let modelContext: ModelContext
    private let aiService = AIService()

    var cards: [AgentCard] { session.cards.filter { $0.state != .discarded } }

    func submitText(_ raw: String)                 // text path
    func submitPhoto(_ image: UIImage) async        // photo path (demo/real)
    func answer(cardID:, field:, value:)
    func edit(cardID:, field:, value:)
    func skip(cardID:)
    func confirm(cardID:, acknowledging:) -> Bool    // performs the .persist effect
    func discard(cardID:)
}
  • Owns the single ModelContext writer. The .persist effect from confirm is the only place a BillRecord is created — single-writer rule stays structural.
  • Holds the RecordingSession by value and republishes cards via @Observable.
  • Photo extraction runs in a Task (async AIService); the result is applied back on the main actor. Text extraction is synchronous and local.
Photo-path settings plumbing: the coordinator owns a ModelContext, so it reads the settings singleton via AppSettings.getOrCreate(context:) and calls aiService.recognizeBill(images:provider:model:apiKey:demoMode:) with: provider = settings.selectedProvider; model = settings.customModel.isEmpty ? provider.defaultModel : settings.customModel (mirrors BillImportFlowView); apiKey = settings.apiKey; demoMode = settings.demoMode. Real (non-demo) extraction is gated on settings.hasConsentedToAIDataSharing, reusing the existing consent sheet. The text path touches none of this.

Field-mapping contracts (avoid two easy traps)

  • DraftExtractor emits BillCategory raw values (food, transport, accommodation, …), not display names — otherwise BillValidator flags every category as unknown. Its unit test asserts raw values.
  • AIRecognitionMapper maps an unparseable date to rawDateText: AIRecognitionResult gives parsedDate: Date? (nil on failure) plus the raw date string — set draft.date = result.parsedDate and, when that is nil but result.date != nil, draft.rawDateText = result.date, so the "date hard to read" gap path is exercised. An unknown result.category is carried to categoryRaw verbatim so the validator can flag it.

Clarify affordances — date & category (user feedback)

  • Date — quick chips + a real picker. The date clarify offers Today and Yesterday chips for the common case, plus a "Pick a date…" control that opens a SwiftUI DatePicker (graphical) for any specific day — e.g. a receipt from earlier in the trip. All three resolve via answer(cardID:, .date, .date(chosen)); the core already accepts an arbitrary date, so the picker is UI-only. The "Pick a date…" picker is also the resolver for the unparseable-date gap (rawDateText != nil), which carries no chips. Reuse Date.relativeLabel (existing in Extensions.swift) for chip/card date labels so a "Yesterday" pick and the Yesterday chip render identically.
  • Category ("tag") — always one-tap changeable at recognition time. Every card renders its category as a tappable chip (icon + name). Tapping opens the 10-category picker (the grid reused from AddBillManualView), so the user can correct it the moment the card appears, not only when the agent is unsure. The agent cannot detect a valid-but-wrong category (it's not a gap), so the fix is to make the chip always editable rather than to add a clarify prompt. An unknown category is still highlighted via the validator's category gap; a confident guess is still one tap from change.
  • Category value contract (must-get-right). The picker iterates BillCategory.allCases, shows category.englishName as the label, and passes edit(cardID:, .category, .category(category.rawValue)) — the rawValue, never the label. Three labels differ from their raw value (Hotel→accommodation, Fun→entertainment, Other→misc); passing the label would store a non-BillCategory raw and re-flag the category as unknown. This mirrors how AddBillManualView binds the enum case, not the label.

4Data flow

Text path (E2E primary, no network)

  1. submitText("ramen 2840") → session.enqueue(.text) → DraftExtractor.parse(...)
  2. Extracts amount (first number), category (keyword map), merchant (leftover words), date nil
  3. completeExtraction → effects
  4. No date → validate raises a date gap (chip "Today") → card enters clarifying
  5. User taps "Today" → answer(.date) → re-resolve → review
  6. User taps Save → confirm → .persist → insert BillRecord into the journal, save()

Photo path

PhotosPicker → submitPhoto → enqueue(.photo) + beginExtraction (LLM budget) → aiService.recognizeBill(demoMode:) → AIRecognitionMapper → completeExtraction. Demo mode returns hardcoded results → deterministic. Real mode reuses the existing consent gate.

Missing amount (adversarial case) — the real 3-step sequence. submitText("ramen") → draft with amount == nil and date == nil. validate returns both a date gap (chip "Today") and an amount gap (no chip options). Per resolve(), only the askable date gap opens a round, so the card first enters clarifying and asks the date chip. After the user answers it, re-validation surfaces the still-missing amount → the card moves to review with Save blocked (ConfirmError.amountRequired) until the user taps the amount field and enters a value (edit(.amount)). So a no-amount text input is a three-step recovery: answer date → enter amount → Save. (The design prototype and E2E §8 #2 follow this exact order.)

5Persistence & schema

  • No SwiftData schema change in v1. Confirmed bills are created exactly like the manual flow (status: .confirmed), so the store stays at BillMindSchemaV1 — no migration risk. sourceSessionID/audit is a SchemaV2 follow-up.
  • Drafts live only in the coordinator's in-memory RecordingSession. Leaving the tab / app discards unconfirmed drafts; nothing partial is persisted.
  • Switching journals rebuilds the session. The validator's journalCurrencyCode is baked in at construction, so the journal selector reconstructs the coordinator (new validator + currency) and discards unconfirmed drafts. A one-line confirm guards against losing in-flight cards.
  • Dateless confirm → today. BillRecord.date is non-optional. The date chip's "Today" is an explicit choice, so a confirmed draft normally has a date. If a draft is somehow confirmed with date == nil (e.g. the user skipped the date round), the coordinator records it with Date() — matching the manual flow's default DatePicker value — and the card shows "dated today". This is a documented fallback, not a silent guess of an arbitrary date.

6Concurrency (Swift 6)

  • RecordingCoordinator is @MainActor; it owns the card array and the only modelContext.insert/save.
  • RecordingSession, BillDraft, and the effect/question types are Sendable value types.
  • Photo extraction is structured: a Task awaits AIService, then applies the mapped draft on the main actor. No bare-Task @State mutation (avoids the BillImportFlowView anti-pattern flagged in review).

7Consent & cost

  • Text path needs no AI → no data leaves the device → no consent prompt. (This is the E2E path.)
  • Photo path: real AI reuses the existing consent gate; demo mode bypasses it. The session's llmCallBudget caps extraction calls.

8Test plan

Unit (XCTest)

  • DraftExtractorTests: amount parsing ("ramen 2840", "2,840", decimals), category keyword mapping, merchant extraction, no-amount → draft with amount == nil, currency carried from journal.
  • AIRecognitionMapperTests: maps merchant/amount/category/currency/lineItems; unknown category preserved (so validate flags it); nil amount preserved.
  • RecordingSessionTests (extend): edit(...) pins the field and clears its gap; editing the category to a valid rawValue clears the category gap.
  • BillValidatorTests (tighten testMissingDateRaisesAnswerableGap): assert the date gap's options are exactly ["Today", "Yesterday"] and that Yesterday's value equals today − 1 day (the injected today is fixed, so the Date is deterministic) — so the Yesterday addition is locked in, not just "options non-empty".

E2E (XCUITest) — adversarial, three cases

  1. Happy/clarify + correction: create a journal → Record → select journal → type ramen 2840 → answer the date chip (and, in a variant, use "Pick a date…" to set a specific day) → tap the category chip and change the category → Save → assert the bill appears with the chosen category, merchant, and amount, and the count increments.
  2. Missing-amount blocked (3-step): type ramen → answer the date chip ("Today") → card is now in review with amount required → assert no bill is persisted (the journal count stays 0) → edit the amount → Save → the bill now persists.
  3. Discard: a card can be discarded and never reaches the journal.

All E2E uses the text path (no API key) and the existing --uitesting-reset for a deterministic store — now extended to also mark the first-launch welcome notice as seen, so the notice doesn't derail this flow (see design/first-launch-notice/SPEC.html). Assertions check the bill in the journal (navigate to JournalDetailView, reusing the existing '2,840' OR '2840' matcher), not the in-memory Record thread.

10Definition of done (all roles check against this)

  • Record tab present and reachable; selecting a journal enables capture.
  • Typing ramen 2840 produces a card; the missing date is asked with Today/Yesterday chips plus a "Pick a date…" picker for a specific day; answering it makes the card saveable.
  • The category is a tappable chip on every card and can be changed via the 10-category picker at recognition time, even when the agent was confident.
  • Save writes exactly one BillRecord into the selected journal (appears in the journal, count + total update) and persists across relaunch.
  • A card with no amount cannot be confirmed until an amount is entered (the agent's core guarantee holds in the UI).
  • No SwiftData schema change; existing flows (manual add, import, Minds, stats) still work.
  • App builds; all unit tests pass; the adversarial E2E passes on the iPhone 17 Pro simulator.
  • No regressions: the existing 59 tests + the create-journal/add-bill E2E still pass.
  • Screenshots captured: empty Record state, a card mid-clarify, a saved bill in the journal.
