BillMind 2.0 · Product Requirements · authored by Coordinator · pipeline step 1

From a local app to a shared, synced service

BillMind becomes a cloud-backed travel-expense companion: accounts, multi-device sync, server-side AI recognition, collaborative trips, and backup — across an iOS app and a web client, on your own VPS. The verified agent core is ported; the home merges Record + Journals in a fresh design.

clients iOS + web auth Apple + Google host your VPS core agent ported server-side

1Problem & vision

BillMind v1 is local-only. That means: no sync across a traveler's phone/tablet/laptop; no way to share a trip with the people you're travelling with; the AI provider key sits in plaintext on every device (a real security hole the audit flagged); and no backup — lose the phone, lose the trip.

Vision: a travel-money companion where you sign in once, capture bills by talking to the agent (recognition runs server-side, no key on the device), and your trips sync everywhere and can be shared with companions who split costs with you — reviewable on a web client too.

2Users

  • The multi-device solo traveler — captures on the phone, reviews on a laptop; wants one synced source of truth and a backup.
  • Travel companions — a couple or a group on one trip; want a shared trip, shared totals, and "who paid / who owes".
  • The reviewer — sits down at a browser to tidy up, categorize, and see the numbers for a trip.

3Goals & non-goals

Goals (the product)

  • Accounts — Sign in with Apple and Google.
  • Multi-device sync of trips, bills, settings.
  • Server-side AI recognition — key on the server, clients send images, get structured bills.
  • Collaborative trips — invite companions, split bills, shared totals, who-owes-whom.
  • Cloud backup (a property of sync).
  • iOS + web clients on one backend.
  • Fresh redesign — the merged Record-home ("Voyage" direction); ported agent core.

Non-goals (v1)

  • Real payment settlement (we track who-owes-what; no money movement).
  • Offline-first CRDT conflict resolution — start with simple last-write-wins + per-bill ownership.
  • Live multi-currency FX rates (keep the manual rate).
  • Android client.
  • Enterprise/SSO, audit logs, admin console.

5Recommended delivery phasing

You chose the full vision; delivering it safely means sequencing it. Recommended split (for your confirmation):

PhaseScope
v1 — FoundationBackend on the VPS · Apple+Google auth · accounts · server-side AI recognition · trip/bill sync (single-user, multi-device) · cloud backup · the rebuilt iOS Record-home · a minimal web client (sign in, view trips/bills, basic capture).
v2 — Collaboration & webShared trips, invites, roles, bill splitting, per-person balances · a fuller web client (capture + edit + stats) · realtime-ish updates.
Why phase it: the synced single-user foundation (auth + sync + server AI) is the backbone everything else needs; collaboration is the most complex slice (multi-user permissions, splitting, conflict). Landing the foundation first de-risks the whole thing and gives you a usable product sooner. The pipeline's gates apply per phase.

6Hosting & constraints

  • Host: your existing VPS. The Backend Worker designs for it (service + database + reverse proxy + TLS); ops and resource limits are yours.
  • Cost shift: AI recognition is now billed centrally to one key — needs per-account quotas / rate limits so one user can't run up the bill.
  • Agent core: the verified Swift agent core (validation, extraction, the card state machine) is ported to the server. Whether the backend is Swift (reuse directly) or another stack (re-implement) is a tech-phase decision for the Backend Worker.

7Privacy — a real posture change

This inverts BillMind's headline promise. v1 said "your data stays on this device, no servers, no account." v2 has accounts and a server holding users' financial data and receipt images, plus server-side AI. The privacy policy, the App Store data declarations, and the first-launch notice copy must all be rewritten to reflect cloud storage + accounts. This is a product/legal requirement, not a detail — called out here so it's owned from the start.

8App Store compliance (Apple)

Going server-backed with accounts triggers mandatory, approval-gating Apple requirements. These are first-class scope, not polish.

9Success criteria

  • A user signs in with Apple (or Google) on two devices and sees the same trips and bills.
  • Capturing a bill from a photo works with no provider key on the device (recognition runs server-side).
  • A trip and its bills survive deleting + reinstalling the app (restored from the server on sign-in).
  • Per-account AI quota is enforced (a user hitting the limit is told, not silently billed).
  • The web client shows the same trips/bills as iOS for the same account.
  • App Store compliance: Sign in with Apple offered at parity, in-app account deletion works (server data purged), privacy policy + labels + manifest updated, all traffic over TLS.
  • (v2) A companion accepts a trip invite and splits a bill; both see correct per-person balances.

10Risks & open questions (for the kickoff)

  • Privacy/security burden — the server now holds financial data + images; encryption at rest, transport security, account deletion, and a real privacy policy are mandatory.
  • Backend stack — Swift (Vapor/Hummingbird, reuses the agent core) vs Node/TS / Python / Go (re-implement core). Backend Worker decides in the Infra Design.
  • Sync model — simple poll/last-write-wins for v1 vs realtime; conflict handling.
  • Web client framework — and how much it shares with iOS (API contract is the shared surface).
  • Repo structure — keep one repo (monorepo: /server, /ios, /web) or split. Decide before build.
  • Migrating existing local data — on first sign-in, upload the device's local trips/bills to the account.
