Synthesized from the approved DESIGN + TECH specs, the existing iOS codebase, and the locked contract/openapi.yaml. Client-only work, sequenced so the app stays green at every step. Anchored to the real contract: capture is stateless (recognition → Card, confirm is the only write).

Plan update (build-time, 2026-06-14):
  • Slice 3 (adopt shared BillMindCore / delete the iOS Agent fork) is DEFERRED. It is not the "pure refactor" assumed: the shared module also ships BillCategory and AIRecognitionResult, which the app already has its own richer versions of (app BillCategory carries the cat_* AI-icon names the tests assert; app AIRecognitionResult has toBillLineItems() for SwiftData). Adopting the module means deleting the app's versions and re-homing their app-specific bits as extensions across the data layer, views, and tests — a large, risky change that is internal cleanup, off the user-facing critical path. The fork is already unit-tested and identical to the module today, so drift risk is low short-term. Revisit after the re-point lands.
  • Order is now: 1 → 2 → 4 (schema) → 5 (sync) → 6 → 7 → 8 → 9 → 10, with 3 slotted back in as cleanup before release if worthwhile.

Approach

Server becomes the single source of truth; SwiftData drops to a disposable offline cache. The verified shared/BillMindCore agent core is adopted (the iOS Agent/ fork is deleted) so the validator can never drift from the server. The kept RecordingSession/BillValidator clarify-loop is re-seeded from server cards.

Key decisions

Local-first or server source of truth?

Server is the source of truth; SwiftData = disposable cache. Journal/BillRecord @Models kept, extended with serverID/rowVersion/updatedAt/isDeleted/syncState.

Re-implement the capture state machine, or render server state?

Stateless: POST /v1/recognition → Card{draft,gaps,canSave}; clarify locally via the kept RecordingSession/BillValidator; POST /v1/bills/confirm is the only write (422 when amount null). Client never computes figures or recomputes canSave.

Where does the agent core live on iOS?

Depend on shared/BillMindCore (already used by the server); delete BillMind/Agent/* to stop iOS/server validator drift.

Token storage & refresh?

KeychainStore as a typed vault (access JWT + opaque refresh, AfterFirstUnlockThisDeviceOnly); migrate plaintext AppSettings.apiKey out of SwiftData; single-flight 401 refresh in the APIClient actor, retry once, sign out on failure.

Where does new networking code land?

APIClient actor + DTOs → Services/AIService.swift; helpers → Utils/Extensions.swift; accounts → Utils/KeychainStore.swift; V2 schema → Models/BillMindSchema.swift. SyncEngine actor is the one justified new file.

Tab structure target?

5 tabs → 4 (Record/Stats/Minds/Settings). Journals removed; its browse folds into Record as the ledger layer. Journal→Trip is a copy rename. Sequenced last.

Risks & watch-items

  • Capture is stateless. An earlier integration map cited card-intent routes (/agent/cards/…) that do not exist in openapi.yaml or the server. Plan is anchored to the contract: recognition → Card, then confirm.
  • Voice/STT undecided (on-device Apple Speech vs server STT). Treated as server-dependent in slices 7/8; flag for PM.
  • Settings not synced — the sync contract defines only trip + bill. Keep AppSettings device-local; move secrets to Keychain.
  • SwiftData V2 migration on a populated V1 store must be tested — a mishandled migration can mask data loss as an empty cache.
  • Decimal money discipline — any Double decode of amount/total breaks NUMERIC(16,2) + never-guess. Slice-1 DTO tests are the guardrail.
  • Apple compliance is load-bearing — Report-this-reply on every agent surface (build-blocking) and Delete account must call DELETE /v1/account (not sign-out). Last two slices; must not be dropped.
