Server topology

REQUEST PATH (Vapor on the VPS): Client (iOS URLSession actor / web TanStack Query) -> Caddy (TLS termination, HSTS, HTTP/2, ACME) -> Vapor HTTP server (single binary, multi-threaded NIO event loops) -> Middleware chain (RequestID -> StructuredLogger -> CORS -> ErrorEnvelope -> RateLimit -> Auth(JWTBearer) -> RouteAuthz) -> Controller (thin; decode DTO, call service) -> Service layer (business logic, transactions) -> Repository layer (Fluent/PostgreSQL via connection pool) -> Postgres. Blob reads/writes go Controller/Service -> BlobStore protocol (LocalDiskBlobStore v1) -> encrypted-at-rest volume.

  1. LAYERS (clean, one direction of dependency, inner layers Foundation-only):
  2. BillMindCore (shared SwiftPM module, /shared in monorepo, imported by BOTH /server and /ios) — the VERIFIED AGENT CORE ported verbatim: Validation.swift (BillValidator, ValidationGap, ClarificationQuestion/Option/Value), RecordingSession.swift (the pure state machine + SessionEffect + ConfirmError + AgentCard), DraftExtractor.swift (local text capture), CardState.swift, BillDraft.swift (BillDraft, DraftLineItem, DraftSource, BillField), AIRecognitionMapper.swift. All Foundation-only, all Sendable, all value types. ZERO edits to these files — they are dropped in. Also moved here so both server and client share one definition: BillCategory enum (raw values are the validator's knownCategoryRaws), AIRecognitionResult Codable. This is the literal answer to 'the verified core is the product core': the server's verification gate IS the same struct the iOS client unit-tested.
  3. DTO/Contract layer (generated from OpenAPI; Swift side hand-validated against the generated TS) — CardDTO, BillDTO, TripDTO, envelope, SSE event payloads.
  4. Domain/Service layer (Vapor-side): AuthService, SyncService, RecognitionService, AgentService (the runtime loop), QuotaService, AccountService(delete/purge), BlobService. These are NOT in BillMindCore — they touch DB/network/disk.
  5. Persistence: Fluent models + migrations over Postgres.

WHERE THE SHARED CORE SITS: BillMindCore is the deepest layer with no Vapor/Fluent/Postgres import. The server's RecognitionService maps a provider response -> AIRecognitionResult -> AIRecognitionMapper.draft(...) -> BillDraft, drives a server-held RecordingSession through validate/clarify/confirm, and only on the SessionEffect.persist writes a Bill row. Card state is therefore server-authoritative because the RecordingSession instance lives on the server (keyed by session id in a short-lived in-memory + Redis-or-Postgres-backed store), and the client only renders the CardDTO the server serializes from AgentCard. The client keeps DraftExtractor for the offline text-capture fallback — the ONE piece of the core that legitimately runs on both sides, because it is deterministic and needs no key. The 'never guess money' guarantee is structural: the only code path that writes a Bill is SessionEffect.persist, reachable only through RecordingSession.confirm, which throws unless draft.amount != nil — that invariant is compiled into the shared core, not re-implemented server-side.

02 Infrastructure & deployment

TARGET: the PM's existing single VPS via Docker Compose. No k8s, no managed cloud — matches 'your VPS' and v1 scale.

  • COMPOSE SERVICES (docker-compose.yml at /server/deploy):
  • caddy: official caddy:2 image. Owns :80/:443, automatic TLS via Let's Encrypt (ACME HTTP/TLS challenge), auto HTTP->HTTPS redirect. Caddyfile sets the security headers globally: Strict-Transport-Security: max-age=31536000; includeSubDomains; preload, X-Content-Type-Options nosniff, X-Frame-Options DENY, Referrer-Policy strict-origin-when-cross-origin, Permissions-Policy camera=(), microphone=(), geolocation=(). Reverse-proxies api.billmind.<domain> -> app:8080 and serves the built web SPA static bundle (or proxies to a tiny static container). Mounts a named volume caddy_data for certs. CSP for the web SPA set here (default-src 'self'; connect-src 'self' https://api.billmind.<domain>; img-src 'self' data: blob:; frame-src 'none'; object-src 'none'; base-uri 'self').
  • app: the Vapor binary. Multi-stage Dockerfile — stage 1 swift:6-jammy builds swift build -c release (pulls BillMindCore from the in-repo path dependency), stage 2 swift:6-jammy-slim runs only the binary + Resources. Exposes 8080 on the internal compose network ONLY (never published to host). Reads all config from env. restart: unless-stopped. Runs DB migrations on boot behind an advisory lock (app migrate step or auto-migrate guarded so only one instance migrates).
  • postgres: postgres:16. Named volume pgdata on an encrypted host volume (LUKS/dm-crypt at the VPS disk layer = encryption at rest for the DB). Not published to host; only reachable on the compose network. Healthcheck pg_isready; app depends_on it healthy.
  • (optional v1) redis: for rate-limit counters + ephemeral RecordingSession/agent-run state + SSE fan-out if multi-instance. v1 can run single-instance and keep these in Postgres + in-process, so redis is an additive, non-blocking service.

BLOB STORAGE: BlobStore protocol; LocalDiskBlobStore writes to a blobs named volume on the same encrypted host volume. APP-LEVEL encryption for receipt images: each image is AES-256-GCM encrypted with a per-object key wrapped by a master key from env before hitting disk (defense in depth over the volume encryption, and the form the privacy policy promises). The protocol means an S3/MinIO impl is a drop-in later with no call-site changes.

SECRETS: a .env file on the VPS only (gitignored, never in the image, never in the repo). Compose injects via env_file. Contents: DATABASE_URL, JWT_SIGNING_KEY (or path to a key file), APPLE_OIDC_* (team id, key id, client id, P8 private key path), GOOGLE_OIDC_CLIENT_ID(S), LLM_PROVIDER_API_KEY (the one central recognition+agent key — the whole reason the device key is gone), BLOB_MASTER_KEY, BACKUP_GPG_RECIPIENT/BACKUP_PASSPHRASE. A startup EnvConfig.validate() fails fast (process exits non-zero) if any required secret is missing or malformed — no booting half-configured.

BACKUPS: a cron sidecar (or host cron) runs pg_dump nightly, pipes through gpg --encrypt (or age), and ships the encrypted dump OFF-box to object storage / a second host. Backups are encrypted before they leave the VPS. Documented restore drill. Blob volume snapshotted on the same cadence.

DEPLOY FLOW: git pull on the VPS -> docker compose build app -> docker compose up -d (caddy/postgres unchanged unless their config did). Zero-downtime is not a v1 requirement; a few seconds of 502 during app restart is acceptable and Caddy retries.

Observability

LOGGING: structured JSON logs (Vapor's Logger + a JSON LogHandler) — one line per request with requestId, userId (or anon), method, path, status, durationMs. NEVER log secrets, full tokens (log only a token jti/prefix), receipt image bytes, or full LLM prompt content (log token counts + tool names, not the financial data). Log levels env-controlled.

REQUEST TRACING: a RequestID middleware mints a UUID per request (or honors an inbound X-Request-Id), attaches it to the logger metadata and echoes it in the response header, so a client error report maps to exact server logs. The agent loop threads the requestId into every tool_call_audit row, so a conversation is reconstructable end to end.

COST/USAGE METERING: the ai_usage table IS the metering store — every recognition and agent turn writes input/output tokens, model, and est_cost_usd. A lightweight /v1/account view surfaces usedToday/limit to the user (the quota card). An operator query rolls up per-user and global daily spend off ai_usage, so the 'one central key' cost is visible and the launch-blocking quota is auditable. tool_call_audit gives the parallel correctness ledger (every computed figure).

HEALTH CHECKS: GET /v1/healthz checks DB connectivity (SELECT 1) and BlobStore reachability (stat the blobs dir/bucket), returns version + git commit. Caddy and the ops/cron use it; postgres has its own pg_isready healthcheck in compose; app depends_on postgres healthy. A simple uptime pinger against /healthz is sufficient at v1 scale; alerting can be a single 'is /healthz failing' rule.

04 API design

REST + JSON with a consistent envelope; the agent chat endpoint streams via SSE. Agent tools are server-internal, not public HTTP. OpenAPI is the single source of truth — TS types are generated from it and the Swift DTOs are validated against it.

SINGLE SOURCE OF TRUTH: /shared-openapi/openapi.yaml (OpenAPI 3.1) is the only contract. CI generates /web/src/api/types.ts via openapi-typescript and runs a Swift contract test that decodes the spec's example payloads into the hand-written Vapor Content DTOs (Swift DTOs are authored to match BillMindCore value types, not blindly generated, because their shapes are pinned by the verified core). A PR touching any endpoint MUST touch openapi.yaml, which re-runs both. All shared enums (CardState, BillField, BillCategory[10 raw values], DraftSource, GapDTO.field, GapDTO.severity, ClarifyValueDTO.kind, AnswerDTO.kind, error.code) are declared ONCE in openapi.yaml components so server/iOS/web cannot drift.

VERSIONING: path-prefix /v1 on every route (both specs already agree). Breaking changes => /v2; additive fields are non-breaking and never require a version bump. The SSE event-type set is versioned with the same /v1 (a new event type is additive; renaming/removing one is breaking).

ERROR ENVELOPE (canonical, applies to every REST response — SSE frames are NOT enveloped): Envelope<T> = { success: bool, data: T?, error: { code: string, message: string, retryable: bool }?, meta: { requestId: string, page?, limit?, total?, syncCursor? }? }. error.code is the machine-readable enum: token_expired | quota_exceeded | conflict | amount_required | needs_acknowledgment | not_reviewable | validation_failed | not_found | forbidden | unauthorized | rate_limited | server_error. message is human copy for inline display; retryable drives the client Retry affordance. requestId echoes the X-Request-Id response header for log correlation.

HTTP-status-to-code map (pinned so 401-refresh and confirm-error handling are deterministic): 401 + token_expired => client coalesced refresh-then-retry-once; 401 + unauthorized (refresh dead) => sign out. 409 + conflict => sync/LWW reconciliation, body carries current server row. 422 maps the three ConfirmError cases: amount_required | needs_acknowledgment | not_reviewable (backend originally listed these as 422; frontend listed amount_required at the envelope level — unified: confirm failures are 422 with the specific code; the calm UI reads error.code, not the status). 429 + quota_exceeded => calm quota card carrying QuotaDTO.

HOW SSE TURNS ARE TYPED: POST /v1/agent/chat with Accept: text/event-stream returns text/event-stream; each frame is event: <type>\ndata: <json>\nid: <seq>\n\n. The id enables Last-Event-ID resume (card state is server-held in agent_session, so a turn is resumable). The canonical event-type union (reconciled from the two divergent lists) is: thinking (status named by the running tool, e.g. {toolName, label:"Adding up 8 bills…"}) | tool_result (AnswerDTO — the typed computed payload) | card (CardDTO) | message_delta (assistant prose delta; MUST NOT contain a figure — QA invariant) | recap (a tool_result with kind=recap; kept as its own event for the day/trip recap card OR folded into tool_result.kind — DECISION: folded into tool_result with kind=recap, so the event set is {thinking, tool_result, card, message_delta, error, done}) | error ({code, message, retryable}, un-enveloped) | quota_hit (carries QuotaDTO; emitted instead of any model call when QuotaService pre-flight fails) | done (closes the turn). Each data payload is a named OpenAPI component (SSEThinking, AnswerDTO, CardDTO, SSEMessageDelta, SSEError, QuotaDTO) so the SSE channel is as contract-governed as REST. A client sending Accept: application/json gets a single non-streamed 200 Envelope with the terminal card/answer (web v1 uses this for single computed answers; full streaming thread is iOS-only in v1).

NAMING UNIFICATION (the two specs used different paths; OpenAPI pins the backend's set as canonical because it is the more complete/RESTful): agent chat = POST /v1/agent/chat (NOT /agent/turn). Card intents = POST /v1/agent/cards/{id}/{answer|edit|setMerchant|skip|confirm|discard} (plural 'cards', NOT /agent/card/{id}). Sync pull/push = GET/POST /v1/sync (NOT /sync/changes); the response body type is named SyncChangesDTO. Image upload/fetch = POST /v1/images, GET /v1/images/{id} (NOT /blobs/{key}); BillDTO.imageRefs carries image IDs resolved via GET /v1/images/{id}, not raw blob keys or baked URLs. Account = GET/DELETE /v1/account; the frontend's GET /me is an alias resolved to GET /v1/account.

05 The AI agent runtime

Never guess money — structural, not prompted

The only code path that writes a Bill is SessionEffect.persist, reachable only through RecordingSession.confirm, which throws unless draft.amount != nil. That invariant is compiled into the shared core. Every figure the agent states is the output of a deterministic tool over the DB; the model never emits numbers, and a tool_call audit row records each computed result.

06 Auth & account deletion

VERIFICATION: Apple and Google at parity (Guideline 4.8). The client performs the native/web OIDC flow and sends the resulting ID token to POST /v1/auth/{apple|google}. The server verifies the JWT fully server-side: signature against the provider JWKS (cached, key-rotation-aware), iss, aud (our client id(s)), exp, and the nonce echoed from a single-use oidc_nonce row (replay/CSRF protection on the web callback). Apple's authorizationCode can be exchanged for the relay relationship; we request only name + email.

SESSION MODEL: short-lived ACCESS JWT (~15 min, HS256/EdDSA signed with JWT_SIGNING_KEY from env) carrying { sub: userId, iat, exp, jti } — stateless, validated by JWTBearer middleware on every bearer route. Plus an OPAQUE, REVOCABLE refresh token (random 256-bit, returned once, stored only as SHA-256 hash in refresh_token). POST /v1/auth/refresh rotates: issue new pair, revoke the old row; refresh-token reuse (a revoked token presented again) revokes the whole chain for that user — theft detection.

REVOCATION: because refresh tokens are server-stored and hashed, logout (revoke this row) and DELETE /account (revoke all) are real server actions, not just client-side forgetting. Access tokens are short enough that revocation latency is bounded by their TTL; a denylist of jti is optional and not needed at v1 scale.

IDENTITY LINKING: identity is keyed on (provider, subject), separate from user, so a single user can hold both an Apple and a Google identity (and a future 'link account' flow can attach a second provider). Login lookup: find identity by (provider, sub); if absent, create user+identity; if present, return its user. NEVER match on email — Apple may give a relay or nothing on later logins.

APPLE PRIVATE-RELAY: the relay address is stored as primary_email with is_private_relay=true on the identity; we treat email as opaque and never as a join key. No outbound email is required for v1 auth, so relay forwarding setup is not on the critical path.

DELETE /account PURGE SEQUENCE (Guideline 5.1.1(v), ordered, idempotent, in one DB transaction where possible): (1) revoke all refresh_tokens; (2) delete tool_call_audit + ai_usage + chat_message + agent_session (the 'LLM logs'); (3) for every receipt_image: delete the blob bytes from BlobStore THEN the row (blob first so a crash leaves no orphaned plaintext); (4) delete bill_line_item -> bill -> trip (cascades cover children); (5) delete identity rows; (6) delete the user. A post-purge assertion (used by QA) confirms zero rows remain across every user-scoped table and zero blobs under the user's prefix. Re-invoking on an already-deleted account returns success.

07 Sync model

MODEL: offline cache + poll + per-bill last-write-wins. SwiftData on iOS is the local cache/offline mirror; the server is the source of truth. No CRDT (explicitly out of scope).

PER-ROW VERSIONING: every syncable entity (trip, bill — line items travel inside their bill) carries row_version BIGINT and updated_at TIMESTAMPTZ. Any server-applied mutation increments row_version and stamps updated_at. Soft-delete is a tombstone: deleted_at set, row_version bumped, row retained so peers learn of the deletion.

PULL (GET /v1/sync?since=<cursor>): the cursor is an opaque high-water mark (encodes max(updated_at)+a tiebreaker, or a monotonic server sequence). Returns all trips/bills with updated_at/row_version beyond the cursor, INCLUDING tombstones (rows with deleted_at), plus a deletions convenience list, plus the next cursor. First sync = since absent = full account snapshot (this is also restore-on-reinstall: sign in, pull everything).

PUSH (POST /v1/sync): client sends upserts + deletions, each tagged with the row_version it last saw (baseVersion). CONFLICT RULE (per-bill LWW): for each incoming row, the server compares — if incoming.baseVersion == server.row_version, apply and bump (clean update); if incoming.baseVersion < server.row_version (someone else changed it first), the LATER updated_at WINS. Server-wins is the default tiebreak when the server copy is newer; the loser (the client's discarded edit) is RETURNED in conflicts[] with the current server BillDTO so the client overwrites its local copy — no silent data loss, the user just sees the server value (matches the design's 'optimistic local write, sync reconciles behind a hairline'). Because the LWW unit is the individual bill, two devices editing different bills in the same trip never conflict.

TOMBSTONES: a delete is an upsert of deleted_at; LWW applies identically (a later edit on one device can resurrect-vs-delete by timestamp — last write wins, deletion included). Tombstones are pruned server-side after a safe retention window (longer than any plausible offline period).

FIRST-SIGN-IN LOCAL-DATA MIGRATION (idempotent): on first authenticated sync, the iOS client uploads its pre-account local trips/bills via POST /v1/sync as upserts. Idempotency: each local row carries its stable client-generated UUID as the primary id; the server upserts by id, so re-running the migration (app reinstalled, flaky network, retried) cannot duplicate — a second upload of the same id is a no-op LWW. A per-device 'migrationCompleted' flag plus the id-based upsert makes the import safe to retry. Receipt images migrate via POST /v1/images then attaching the returned ref. This is the PRD's 'on first sign-in, upload the device's local trips/bills to the account', made idempotent.

OFFLINE: text capture works locally via DraftExtractor (the shared core, no key); the confirmed bill is queued and pushed on reconnect through the same POST /v1/sync path. Photo-recognition and agent Q&A are honestly disabled offline (they need the server key).

08 iOS client

CLIENT IS A THIN RENDERER OF SERVER-AUTHORITATIVE STATE. The agent core (RecordingSession/AgentCard/CardState/BillValidator) runs on the SERVER; the iOS app never re-implements the state machine — it renders the CardDTO the server emits and sends intents back. The only client-side core reused VERBATIM from /shared-openapi's sibling SwiftPM module is DraftExtractor (Foundation-only) for offline text drafts.

LAYERS (bottom-up):

1) APIClient (actor over URLSession). Single networking choke point. Holds baseURL, a JSONEncoder/Decoder configured for the wire contract (ISO8601 dates with fractional seconds; Decimal money decoded from JSON string, NEVER Double — custom KeyedDecoding that reads amounts as String then Decimal(string:)). Exposes func send<T: Decodable>(_ endpoint: Endpoint) async throws -> Envelope<T>. All responses are the consistent envelope (success/data/error/meta). Injects Authorization: Bearer <access JWT> from TokenStore. ATS enforced, no exceptions; TLS only (matches Caddy/Let's Encrypt on the VPS).

2) Auth + 401 refresh. On a 401 with code token_expired, APIClient suspends the failing request, calls AuthService.refresh() ONCE (serialized via an actor-isolated in-flight Task so concurrent 401s coalesce into a single refresh), swaps the new access JWT, and retries the original request once. Refresh uses the opaque REVOCABLE refresh token. If refresh fails (revoked/expired) → publish .signedOut, clear Keychain, route to Auth. Sign-in is Apple (ASAuthorizationController) + Google (ASWebAuthenticationSession) at button parity; both POST the provider identity token to /auth/{apple|google} and receive {accessToken, refreshToken, user}.

3) TokenStore — generalize the existing KeychainStore into a typed token vault: accessToken (short-lived JWT, also cacheable in-memory), refreshToken (opaque, Keychain only, kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly), userID. No tokens in UserDefaults/SwiftData. DELETE /account and sign-out both purge the Keychain items.

4) SwiftData = OFFLINE CACHE ONLY, not source of truth. Local @Model mirrors of server rows: CachedTrip, CachedBill, CachedLineItem — each carries serverID: UUID, rowVersion: Int, updatedAt: Date, isDeleted: Bool (tombstone), and syncState: SyncState (.synced/.pendingCreate/.pendingUpdate/.pendingDelete/.conflict). The store is disposable (matches existing "auto-reset on migration failure" posture) because the server is canonical — a wipe re-hydrates from the delta endpoint on next sign-in.

5) SyncEngine (actor). Owns reconciliation. Pull: GET /sync/changes?since=<cursor> → applies server rows by per-bill LAST-WRITE-WINS using rowVersion (higher wins) then updatedAt as tiebreak; honors soft-delete tombstones. Push: drains the pending-mutation queue (optimistic local writes already applied) → POST/PATCH/DELETE; on 409 conflict the server returns the authoritative row, SyncEngine overwrites local and surfaces a non-blocking "synced from another device" note (LWW, no merge UI in v1). Triggers: app foreground, post-confirm, pull-to-refresh, and a lightweight poll while Record is visible (no realtime in v1). Cursor (opaque since token) persisted in UserDefaults.

6) Optimistic writes. Confirming a draft, editing a saved bill, creating/renaming a trip: write to SwiftData immediately with syncState=.pending*, render instantly, enqueue the mutation. The ledger "count-up" animation runs off the optimistic local total. Rollback on terminal failure restores the snapshotted row and shows an inline Retry (never a raw error).

7) SSE via URLSession.bytes. The agent/chat surface is a stream, NOT polled. AgentStream opens POST /agent/turn (or /agent/session/{id}/events) with Accept: text/event-stream and iterates for try await line in bytes.lines, parsing SSE frames into typed AgentEvents (see agentRendering). The stream is the ONLY way card state and answers arrive during a turn; the client renders whatever CardDTO/AnswerDTO the server pushes and never advances the state machine itself. Reconnect with Last-Event-ID on drop; a turn is resumable because card state is server-held.

8) The staged capture rail renders a server-driven CardDTO. The five stages (Input→Recognition→Verification→Clarification→Confirm→Push) are exactly CardDTO.state (intake/extracting/validating/clarifying/review/recorded/failed/discarded mirrored from CardState). The rail is a pure function of CardDTO: gaps[] → the always-rendered checklist; openQuestions[] → chip rows; amountResolved==false → Save disabled (the hard gate, mirroring BillValidator.amountGap). User actions POST intents (/agent/card/{id}/answer, /edit, /skip, /confirm, /discard) and the resulting new CardDTO streams back over SSE. CONFIRM is the only intent that triggers a server write + a BillDTO appearing in the synced ledger.

9) Local DraftExtractor fallback applies ONLY to offline text capture: when offline (or server unreachable) and the user types "ramen 2840", the app calls DraftExtractor.parse locally to show an editable draft and a "needs amount"/"needs date" rail computed by a LOCAL BillValidator copy, queued as a pendingRecognition. Photo, voice, and any Q&A are disabled offline with honest copy (they require the server-held provider key + agent loop). On reconnect the queued text draft is replayed to the server, which becomes authoritative.

MVVM-ish: SwiftUI Views observe @Observable view-stores (RecordStore, TripStore, AgentSessionStore) that read the SwiftData cache and call the actors. No business logic in Views; no number formatting that isn't fed by a server-computed value (the never-guess rule extends to the UI — see agentRendering).

HONEST DEGRADATION, not an infinite spinner. Capability split by what needs the server-held provider key + agent loop:

- RECONCILE ON RECONNECT: SyncEngine first PUSHes the PendingQueue in order (text drafts → confirm intents, edits, deletes), then PULLs /sync/changes. - WEB has NO offline mode (no Keychain, no DraftExtractor fallback shipped to web in v1): it shows a plain 'you're offline' state and resumes via TanStack Query revalidation on reconnect. Conflicts resolved

1) BillDTO.status enum: frontend declared 'draft'|'confirmed'; backend persists no draft row at all (a Bill exists only after RecordingSession.confirm fires SessionEffect.persist, so amount is non-null by construction). RESOLVED: BillDTO.status is fixed to 'confirmed' (single-value enum kept for forward-compat). The 'draft' concept is owned exclusively by CardDTO/CardState; it never appears as a Bill row or in BillDTO. This keeps the never-guess invariant structural.

2) canConfirm / amountResolved: the frontend's CardDTO carries these, but they do NOT exist on the core's AgentCard struct. RESOLVED: they are SERVER-DERIVED projection fields — amountResolved = (draft.amount != nil); canConfirm = (state==.review && draft.amount != nil && carriedGaps acknowledgeable). The server computes them from BillValidator + RecordingSession.confirm preconditions; the client renders Save-disabled from amountResolved/canConfirm and NEVER recomputes confirmability (the offline LocalValidator copy is reconciled server-wins on reconnect). This makes card state genuinely server-authoritative.

3) GapDTO.severity: ValidationGap in the core has no severity field. RESOLVED: severity is a server-assigned projection — field==amount => 'hard' (the only confirm-blocking gap, matching ConfirmError.amountRequired), date/category/currency => 'soft'. Verified merchant never produces a gap (Validation.swift has no merchant rule; setMerchant is a separate non-validating path), so GapDTO.field correctly excludes merchant while BillField (used by pinnedFields/carriedGaps/QuestionDTO.field) keeps all five.

4) Endpoint path divergence: frontend used /agent/turn, /agent/card/{id}/*, /sync/changes, /blobs/{key}, GET /me; backend used /agent/chat, /agent/cards/{id}/*, /sync, /images, /account. RESOLVED in favor of the backend's set as canonical (more RESTful/complete), with GET /me kept as an alias of GET /v1/account. Frontend modules re-point to the canonical paths; this is a client-side rename only, no shape change.

5) SSE event-type divergence: backend listed thinking|tool_result|card|message_delta|done; frontend listed assistant_text|tool_result|card|recap|error|done. RESOLVED to one union {thinking, tool_result, card, message_delta, error, done} plus quota_hit. assistant_text==message_delta (prose delta; MUST carry no figure). recap is folded into tool_result with kind=recap rather than a separate event. error and quota_hit added explicitly (both specs need them).

6) Two number-bearing shapes (backend tool_result payload vs GET /stats vs frontend AnswerDTO): RESOLVED to a single AnswerDTO with provenance (basis/billIds/computedAt). GET /v1/stats returns the same breakdown shape so the Stats tab and an embedded answer chip use one rendering path — 'computed' is one component, one contract.

7) Image addressing: frontend referenced opaque blob keys + GET /blobs/{key}; backend has POST/GET /v1/images with imageId and a receipt_image row keyed by blob_key internally. RESOLVED: the wire exposes imageId only (BillDTO.imageRefs = [imageId]); blob_key stays a server-internal detail behind BlobStore. No raw URLs are ever baked into a row.

8) QuotaDTO field-name drift between GET /account's inline quota and the standalone QuotaDTO: RESOLVED to one QuotaDTO {tier, aiCallsUsedToday, aiCallsLimit, resetsAt, blocked} used in all three surfaces (account view, 429 error, SSE quota_hit).

9) Web refresh-token transport: frontend specifies HttpOnly cookie for web vs Keychain refreshToken for iOS. RESOLVED: AuthTokensDTO.refreshToken is optional and omitted in web responses (cookie-set instead); same /v1/auth/* endpoints, transport differs by client — documented in OpenAPI as a security-scheme note, not two endpoint sets.

Agent evaluation harness — the novel, highest-value piece

SHAPE: a deterministic test table over the agent loop, asserted against the tool_call_audit ground-truth ledger. Each case = {seeded bills (NUMERIC), user utterance, expected: tool(s) called, computed figure(s), final card/answer state, refusal/clarify behavior}. The harness runs AgentService.run with the tool registry pointed at a real ephemeral Postgres (so compute_* aggregate real NUMERIC rows) and the model swapped via a protocol seam. TWO MODES split: (1) MOCK-LLM (CI, every PR, 100% deterministic): the LLM seam returns scripted tool-call sequences, so the loop, tool dispatch, audit writes, and SSE framing are tested without a network or cost — this gates merges. (2) REAL-LLM (nightly / pre-release, non-blocking-on-PR): the actual provider drives tool selection; we assert pass-RATE thresholds, not per-run determinism.

'recap today' ⇒ summarize_period; total/topCategories/notableBills all tool-derived. Each golden case asserts a tool_call_audit row exists whose computed_figures equals the figure shown.

NO-HALLUCINATED-NUMBER TRACE ASSERTION (100% required, launch-blocking invariant): for EVERY case, scan all message_delta SSE frames; assert no frame contains a numeric token that does not appear in a preceding tool_result/card payload AND trace to a tool_call_audit.computed_figures entry. A digit in prose with no backing audit row = hard FAIL. This is the machine form of the design invariant 'if a number isn't in a tool-result component it's a bug.' Pass rate target: 100% in BOTH mock and real modes (a single hallucinated figure blocks release).

TOOL-SELECTION CORRECTNESS: assert the right tool for intent — a total question ⇒ compute_totals; breakdown ⇒ compute_category_breakdown; 'who owes' (v1 single-user) ⇒ compute_balances stub; capture utterance ('taxi 3200') ⇒ recognize_receipt path producing a CardDTO draft, NOT an answer. Mock mode asserts exact tool name; real mode asserts ≥ target accuracy and never-wrong-tool-on-money.

REFUSAL / CLARIFY BEHAVIOR: 'how much will I spend next week?' (uncomputable) ⇒ the agent says it cannot, calls NO compute tool, emits no figure. Ambiguous 'dinner in kyoto' (place, no number, no question word) ⇒ offers the two chips (Add as a bill / Answer a question), creates NO bill. 'what's the GDP of Japan?' (off-domain) ⇒ refuses without inventing a number.

MULTI-FIELD CLARIFICATION (amount HARD / category+date SOFT): drive recognize_receipt on a draft missing amount+category+date. Assert: amount is a HARD gap (GapDTO.severity==hard, canConfirm==false, confirm ⇒ 422 amount_required) and CANNOT be defaulted or saved; category and date are SOFT (severity==soft) — surfaced as questions but skippable, and skip ⇒ carriedGaps + confirm needs acknowledging:true (never silently backfilled — no ¥0, no guessed date). Resolving the amount via a number-pad edit ⇒ re-validate ⇒ canConfirm flips true. This is the exact BillValidator behavior already proven in the core, now asserted through the server agent + DTO projection.

PASS-RATE THRESHOLDS: never-hallucinated-number = 100% (mock + real), launch-blocking. Tool-selection correctness ≥ 95% real / 100% mock. Golden-case figure exactness = 100% mock (deterministic SQL) and 100% real (figures come from SQL, not the model — only tool CHOICE can vary). Refusal/clarify correctness ≥ 90% real / 100% mock. Real-mode runs N≥3 trials/case for stability; any never-hallucinate failure in any trial fails the suite.

Sync / multi-device

  • Two-client convergence: capture on device A, poll-pull on B (GET /v1/sync?since=cursor) returns the new bill; B's cursor advances.
  • Same-bill conflict: A and B both edit bill X with the same baseVersion; later updated_at wins, the loser's edit returned in conflicts[] with the current server BillDTO (no silent loss), client overwrites local.
  • Different-bill non-conflict: A edits bill X, B edits bill Y in the same trip; both apply cleanly, no conflicts[].
  • Tombstone propagation: delete bill on A ⇒ B's next pull carries it via isDeleted + deletions[]; a later edit-vs-delete resolves by LWW timestamp.
  • Restore-on-reinstall: delete+reinstall, sign in, GET /v1/sync with no since returns the FULL account snapshot (all trips, bills, line items, tombstones).
  • Idempotent first-sign-in migration: upload pre-account local rows by stable client-UUID; re-run after a simulated retry/reinstall ⇒ id-keyed upsert is a no-op, zero duplicates (billCount unchanged).
  • hasMore pagination: a delta larger than one page returns hasMore:true and a nextCursor that, when followed, drains the rest exactly once.
  • Line items travel inside their bill (not independently synced); a BillDTO round-trips lineItems with quantity/unitPrice defaulted (1/0) when promoted from a DraftLineItem.
  • Offline capture: DraftExtractor text capture works with no key, the confirmed bill queues and pushes via POST /v1/sync on reconnect; SwiftData mirror reconciles server-wins on reconnect.
  • SSE resume: drop the stream mid-turn, reconnect with Last-Event-ID; the server-held agent_session replays the turn from card state without double-applying (idempotent intents).

Cost / quota & load

  • Quota pre-flight blocks at the tier limit: recognition ⇒ 429 quota_exceeded + QuotaDTO; agent turn ⇒ single SSE quota_hit, ZERO provider calls, ZERO new ai_usage rows.
  • Calm degradation: while AI is quota-blocked, free local DraftExtractor text capture still succeeds end to end (never a hard stop, never a silent bill).
  • Mid-turn enforcement: a turn that would exceed the cap on its second tool-iteration is stopped before the next model call (pre-flight is per-call, not per-session).
  • Runaway-loop bounds: per-turn tool-iteration cap (e.g. 6) ends a spinning turn with a graceful 'couldn't finish'; per-session RecordingSession.llmCallBudget caps extraction calls; assert both fire.
  • Cost metering accuracy: every recognition and agent turn writes an ai_usage row (input/output tokens, model, est_cost_usd, day); the per-day rollup the quota sums equals the seeded usage.
  • Load sanity (v1 scale, not a stress test): a concurrency run (e.g. 50 parallel sync pulls + 20 concurrent agent turns with the mock LLM) holds p95 latency within budget, the Postgres connection pool does not exhaust, no NUMERIC rounding drift under concurrent compute_totals, and tool_call_audit writes are not lost under contention.
  • Rate-limit middleware: bursts beyond the per-account limit return 429 rate_limited (distinct from quota_exceeded) with retryable=true.
  • Account-isolation under quota: one user hitting their limit does NOT throttle another user (per-account counters, verified with two users).
