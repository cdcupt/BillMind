Architecture: held-batch capture → untangle → review → save

Merged infra + backend + frontend + QA plan. Implements design/dedup/PRD.html + design/dedup/DESIGN.html. · v1 · 2026-06-22

1 · Key decisions

Fusion → server (Gemini)

Fusion is reasoning ("does this note complete this photo?"); the agent already lives server-side. Keeps AI-first + concentrates money-safety server-side.

Dedup → client-detected, server-confirmed

Same-photo (asset id + perceptual hash) and merchant+amount+date are mechanical/free on the client; the server confirms in the same round-trip so groups are uniform & testable. Client-only is the degraded fallback.

Untangle does NOT re-recognize

It takes cards the client already got from /v1/recognition and returns a plan referencing their IDs — reuses recognition, preserves money-safety, keeps the body small (no image bytes; photoHash only).

Save path unchanged

Disposition still saves one card at a time via existing POST /v1/bills/confirm (validator-gated). One fused card → one bill. Set-aside duplicates are simply not persisted (no delete).

Schema: no migration (v1)

Provenance is a pre-save review concept only. A fused bill saves as one ordinary Bill (existing source column). Post-save provenance = a future additive table, out of v1.

New: stable clientCardID

The wire CardDTO has no id today; the client assigns a per-session UUID so untangle groups can reference cards. (Small additive DTO change.)

2 · The seam — POST /v1/untangle

Auth + owner-scoped on tripID (same UserAuthMiddleware as recognition). No images in the body → the 1mb global cap is fine.

Partition invariant: every input cardID appears in exactly one of fuseGroups / duplicateGroups / cleanCardIDs. The client validates this against its live cards; any unaccounted card fails open to a plain review card (never dropped). amountTrace is the ONLY amount provenance — null ⇒ client shows "amount required", never invents.

3 · Money-safe fusion (the critical path)

Moderation: recognition already gated each card's text at /v1/recognition; untangle adds no new user free-text, so no re-moderation needed.

4 · Client — held-batch session model

Owner: RecordingSession.swift. Adds a session-level BatchPhase { adding, untangling, reviewing } distinct from per-card CardState (the proven card machine is untouched). Groups are modeled as a groups: [UntangleGroup] value field, not new CardState cases — groups are views over held drafts, so Split / Keep-both are pure discards (no draft is ever mutated at proposal time → reversibility is structural).

Touch-points & fast path

  • Done-adding bar in RecordView.session (sticky, above the input bar) — renders only when cards.count > 1. A6 fast path a lone clean input keeps its instant per-card Save (RecordCoordinator.confirm) and bypasses untangle entirely — single-capture is byte-for-byte unchanged.
  • New views beside AgentCardView: FuseProposalView (resolved card + "made from" provenance strip with amount-source trace + Combine/Split) and DuplicateGroupView (the committed dedup bracket + keep one/both).
  • Save: confirmAll() → one BillRecord per plain card and per accepted fuse, via the unchanged persist mapping; set-aside dups not persisted; existing amountRequired/needsAcknowledgment guards gate each row.
  • Coordinator: new markDoneAdding() (gathers held cards → RecognitionAPI.untangle → applyUntangle), with a calm "Ollie is tidying…" overlay reusing the thinking-state grammar.

5 · Server touch-points

  • New server/Sources/App/Controllers/UntangleController.swift + route in configure.swift (beside the recognition route).
  • New DTOs beside CaptureDTOs.swift (CardDTO gains clientCardID); fusion client modeled on GeminiRecognizer.swift / GeminiLLMClient.swift (strict JSON, thinkingBudget:0).
  • Reuse BillValidator (as in CaptureController); save unchanged at LedgerControllers confirm; no schema migration.

Coverage gaps (where automation is weak — flagged, not hidden)

  • Gemini fusion quality (does this note really complete this photo?) — CI enforces the money guard, not match accuracy; needs a labelled true-fuse / false-fuse / true-dup fixture set + a tracked precision/recall threshold.
  • Perceptual-hash threshold for re-encoded/cropped photos — needs real image fixtures + a tuned Hamming cutoff.
  • Held-state durability across backgrounding — out of v1 (ephemeral); a known gap, not a covered guarantee.
  • A6 "as fast as today" — qualitative; the proxy assertion is "no /v1/untangle call" for a lone input.
  • Re-tidy after a late add — depends on groupID locking not yet pinned; contract gap to close before that behavior is testable.
