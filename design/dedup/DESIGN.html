BillOwl · Design Document · Smart Multi-Input Capture (F5+)

Drop everything in — Ollie untangles it, you confirm

Batch capture with fuse (partials that are one bill), dedup (the same bill twice), and a Done-adding → Review step that holds inputs so the agent can reason over them together — then one Save. Designed within the locked money rule: the agent proposes, the user disposes; nothing merged or dropped silently; a fuse never invents or alters an amount; everything reversible until Save. · v2 · 2026-06-22 · supersedes the F5 dedup-only design (dedup is now Pillar 2)

1 · The three decisions in one line each

Fusion trigger → propose-and-confirm

Ollie proposes a fuse (never auto-merges, never makes the user manually attach). Pre-selected as one card, but Split is one tap and both originals survive intact. This is the only model the money rule allows — see §3.

Review surface → extend the staged-card list

No new screen. The untangle results land as grouped cards in the same scroll the user already saves from, gated by a sticky Done adding → Review bar above the input. Justification in §2.

Single clean input → unchanged

If nothing needs untangling, there is nothing to review. The lone card behaves exactly like today and saves straight through. The batch machinery is invisible until there's a reason for it (A6).

2 · The capture model shift, and where review lives

Today each input becomes its own card the instant it's entered, and you finish a card by editing fields and tapping its own Save. The shift: while you're still adding, cards stage but stay held; the agent waits to reason over the whole batch until you tap Done adding. Fusion requires this — Ollie can't know a note completes a photo until both are in.

The control is a button, never a parsed trigger word (locked PM decision). A magic phrase is undiscoverable and would collide with real bill text ("I'm done eating, ramen 240"). The button lives in a sticky bar above the input so it's always reachable as the pile grows, and it counts what's waiting ("Review 4").

Why extend the list, not build a dedicated review screen. Three reasons. (1) A6 — zero friction. A separate screen forces a transition even when there is nothing to untangle; extending the list lets the clean single-input case stay literally one scroll, one Save. (2) Continuity. The committed dedup design already lives inline on this list; fusion is its sibling and belongs in the same visual grammar (tethered cards, a calm Ollie bar, undoable resolutions). Two different surfaces for two sibling actions would fracture the mental model. (3) Judging by looking. "Are these really one bill?" / "are these really the same?" is answered by seeing the cards side-by-side in the scroll, not by trusting a summary on a handoff screen. Review mode is a state of the existing list, not a new place.

3 · Pillar 1 — Fuse partials (the new hard part)

A photo captures half a bill (amount cut off, or a blurry total); a note supplies the rest ("the total was 240"). Today the note spawns a second card. Fusion combines them into one.

3.1 · Why propose-and-confirm (not auto, not user-directed)

ModelWhat it doesVerdict
Agent-automaticOllie silently merges the photo and note into one card.Rejected. Violates the money rule head-on: a silent merge that pulls "240" onto a receipt is exactly the invisible amount-write the PRD forbids. A wrong guess corrupts a bill with no visible undo.
User-directedThe user manually drags/attaches a note onto a specific card.Rejected as the primary path. Puts the whole burden on the user, defeats "the app sorts it out," and is fiddly on a phone. (Kept as a fallback gesture — §3.4.)
Propose-and-confirmOllie detects the pair, builds a proposed fused card, and shows its provenance with Combine (accept) / Split (reject) — both one tap, both reversible.Chosen. Ollie does the hard reasoning; the human owns the money-bearing decision. Matches the dedup grammar exactly, so the two pillars feel like one feature.
The pick: propose-and-confirm — Ollie does the matching, the user owns the join. It's the only trigger model where the agent helps and the money rule holds: the fused amount is always shown as coming from a named input, never silently stitched in.

3.2 · How a fused card shows its provenance

A proposed fuse is one card with a visible seam: the resolved bill on top, and beneath it a thin "made from" provenance strip showing the two sources as small slips — the photo thumbnail and the note text — each tagging which field it contributed. The amount carries a "from your note" trace so it's obvious the number came from the typed "240", not from thin air. Provenance is the whole safety story made literal: you can see what completed the bill, and where the money came from.

3.3 · How Split works (A5)

One tap on Split (or the seam) dissolves the fused card back into the two original cards, intact — the photo card (still amountless) and the note card (still "taxi 240"). Nothing was destroyed in the proposal: the fuse is a view over two held inputs until Combine is confirmed, so Split is just discarding the proposal. Both survivors return to normal review, and the photo card shows its usual "amount required" gap if it still has one.

3.4 · Money safety after fuse (A7)

The amount is never invented. A fuse only carries a number that a real input supplied. Three outcomes: (a) the note supplies the amount → the fused card is review-ready, amount traced to the note; (b) the photo had the amount and the note added merchant/date → same, traced to the photo; (c) neither input has a readable amount → the fused card lands in the existing "amount required" gap state exactly as a lone card does today (red italic "amount required", Save disabled until entered). Fusion never fabricates a total to "finish" a bill.

Optional power-user fallback: in review, dragging one card onto another offers the same Combine proposal — a manual way to fuse a pair Ollie missed. Still propose-and-confirm (a confirm sheet, not an instant merge), still splittable. Out of v1 scope unless cheap.

4 · Pillar 2 — Dedup (carried from the committed F5 design)

Unchanged in spirit from the prior design — it is the model the fuse grammar copies. When two inputs are the same bill (same photo, OR merchant + amount + date all match), Ollie tethers them and offers Keep one / Keep both.

Tether, not modal

The duplicate pair is bracketed in the dashed sand caution stroke (never red) with one calm "Ollie noticed" bar between them. No new screen.

Keep both is the safe one-tap

The prominent filled-pine button. The escape from a false match is the easiest action; nothing reads as deleted (A3).

Keep one sets aside, never deletes

The non-survivor collapses to a dimmed "set aside" strip with Undo — not destructive-red. Removal happens only on the explicit tap, reversible until Save (A1, A7).

Survivor pre-picked

Same-photo → first card (pixel-identical). Same-details → the richer card (has line items/date), else the photo-sourced one. Always overridable in one tap.

Groups of 3+

One bracket over all N, one decision: Keep one (with a tiny survivor chooser) or Keep all. No nested pairwise prompts.

Two confidence tiers (copy only)

Same photo → firm "the same photo twice". Same details → tentative "might be the same bill". Same actions; warmer tone on the looser match.

5 · Pillar 3 — The review surface & the full state set

The untangle adds two group layers over the existing review state — fuseProposed and flaggedDuplicate — both resolving back to ordinary review cards that flow into recorded. Below is every state the user can land in.

(a) Single clean input

Nothing to untangle. The lone card is a normal review card; tapping its Save (or "Save all") writes it. No Done-adding ceremony forced. A6: zero friction

(b) Fuse proposed

A receipt + a completing note shown as one card with a "made from" provenance strip. Combine / Split. The centerpiece — §6 mockup (b).

(c) Fuse split

One tap on Split → the two originals reappear intact (photo amountless, note "taxi 240"). Both are ordinary review cards again (A5).

(d) Duplicate pair

Two cards tethered; "Ollie noticed" bar with Keep one / Keep both. §6 mockup (c).

(e) Duplicate 3+

All N under one bracket; Keep one (survivor chooser) or Keep all. One group, one decision.

(f) Fuse AND dup in one batch

Both groups render in the same review scroll, each its own tethered bracket, independently resolvable. Save all waits until every group is touched. §6 mockup (d).

(g) Amount still missing after fuse

Neither source had a readable amount → the fused card shows the red "amount required" gap; Save disabled until the user enters it (A7). Fusion never fabricates the number.

How "Save all" stays safe. Review ends in one Save, but it never saves over an open decision. An unresolved fuse or duplicate group keeps a 1-tap default visible (Combine / Keep both — the non-destructive choices) and gently blocks "Save all" until each group is touched, so the user can't accidentally accept Ollie's guesses wholesale. Clean cards in the same scroll save with it. Everything stays reversible until that final tap.

6 · Mockups — the PM review surface

SketchTheme cream paper, white cards, hairline brown borders, serif merchant names, monospaced amounts. Four moments: (a) Done adding, (b) a fuse proposal with provenance, (c) the dedup confirm, (d) the review surface with a fuse and a dup together.

pine — keep / combine / survivor / save terra — Ollie / accent / amount sand-caution — tether bracket + fuse seam (not destructive) muted — set-aside / split (dimmed, undoable) gate-red — reserved; never used to flag a fuse/dup
Money-safety reads, made literal. (1) The fused amount is tagged "¥240 from your note" — the user sees where the number came from; it is never silently stitched in. (2) Combine and Keep both (the non-destructive accepts) are the filled-pine, prominent buttons; Split and Keep one are the quieter outlines. (3) Nothing is removed at proposal time — a split or a set-aside is reversible until "Save all". (4) The bracket and seam use the sand caution stroke, never the destructive gate-red BillOwl reserves for real deletes. (5) If a fuse leaves no readable amount, the card shows the same red "amount required" gap a lone card shows today — Save stays disabled.

8 · Match & fuse tolerances — recommendations for tech

The confirm step is the safety net, so detection should lean strict: a missed fuse/dup is recoverable (the user fixes it by hand, as today); a noisy false flag erodes trust. Dedup tolerances carry from F5 unchanged; fusion adds new ones.

SignalRecommendationRationale
Dup — same photoAsset localIdentifier first; perceptual/diff hash of the downscaled JPEG as fallback. High confidence.Asset identity is exact and free; the hash catches re-encodes of the same pixels.
Dup — detailsFlag on (merchant normalized-exact) AND (amount exact Decimal, same currency) AND (same calendar day). No fuzzy/substring, no amount band.Carried from F5. All three keeps the path strict; two real ¥30 coffees never flag.
Fuse — pairingPair a card missing a key field (esp. amount) with a card that supplies exactly that field, when the others are compatible: merchant/category align (or one side is blank) and dates are same-day or one is undated. A note with only an amount + a noun ("taxi 240") pairs with a same-category amountless photo.Fusion is "these complete each other," not "these are equal." The complementary-gap signal is what distinguishes a fuse from a dup.
Fuse — amount provenanceThe fused amount is taken verbatim from whichever source had it; if both have a (different) amount, do not auto-fuse — that's a conflict, leave them separate (or flag as a possible dup if equal).Money safety (A7): never reconcile two conflicting numbers silently; never average or pick.
Fuse — confidence floorOnly propose when the complementary match is strong (same category + same-day + one clear gap filled). Below that, leave both cards separate — the user can fuse by hand.A false fuse touches money; bias hard toward not proposing over proposing wrongly.
When it runsOn Done adding, over the in-memory held set (post-extraction). Re-run if the user adds more after a review or edits a flagged card's key fields.Fusion needs the whole batch; Done-adding is the natural barrier. Instant on a handful of cards.
Edge: a card still extracting / clarifying isn't eligible for a details dup-match (can't compare a gap), but its gap is exactly what makes it a fuse candidate. Keep the two scans distinct: dup matches on sameness, fuse matches on complementarity.

9 · Open questions for tech

  • Where fuse/dedup runs — client vs server batch endpoint. Dedup is cheap and deterministic → fine on-device over the staged cards (as F5 assumed). Fusion is reasoning ("does this note complete this photo?") and the agent already lives server-side — a batch endpoint (post the whole held set, get back proposed fuses + dup groups) is likely cleaner and keeps the AI-first principle. Tech to decide: one new POST /v1/untangle over the session vs. a client-side heuristic pre-pass with server only for the ambiguous fuses. The PRD explicitly allows a server change here.
  • Match/fuse tolerances (the exact thresholds in §8) — especially the fuse confidence floor and what "compatible merchant/category" means precisely. Needs a small labelled sample from beta data to tune.
  • Held-state persistence. If the app is backgrounded mid-batch (before Done adding), are held cards + their source images restored on return? Recommend yes for photos already uploaded; tech to scope against the session model.
  • Re-tidy after adding more. When the user adds an input after a review, does the whole batch re-scan or only the new card against the set? Recommend incremental (new card vs. existing) to avoid re-proposing already-resolved groups.
  • Provenance after Save. Does a saved fused bill keep its source links (photo + note) in BillRecord for later inspection, or is provenance review-only? Affects the schema.

10 · PRD ambiguities & assumptions

  • "Done adding" with one input (PRD A6 vs. the batch model). Assumed: a lone clean card never requires Done-adding — its own Save still works, and the Done bar just collapses the (trivial) review. The batch step is opt-in pressure, not a mandatory gate, so the single-capture path is unchanged. Flagged for PM.
  • Whether held cards show per-card Save while adding (unspecified). Assumed per-card Save is paused in adding mode (you save the whole tidied batch), but a single card with no batch around it keeps its instant Save — preserving today's fast path. Keeps "the agent reasons over the batch" honest without trapping a one-off capture.
  • Conflicting amounts on a fuse candidate (PRD silent). Assumed: if two inputs both carry a different amount, Ollie does not fuse (it's a conflict, not a completion) — leaves them separate. Strictest money-safe reading of A7.
  • Fuse provenance persistence (PRD open). Assumed review-only for v1 (the seam exists until Save; the saved bill is a normal single bill) unless tech finds keeping the links cheap. Avoids a schema change in v1.
  • Manual fuse gesture (PRD "user-directed" option). Assumed kept as an optional drag-to-combine fallback, still propose-and-confirm, out of v1 unless cheap — so the primary path stays agent-proposed.
