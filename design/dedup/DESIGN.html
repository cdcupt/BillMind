Duplicate-record detection — the confirm experience

How Ollie flags a likely double-add inside a Record session and lets the user keep one or keep both — inline, lightweight, money-safe. Designed within the 3 locked PM decisions. · v1 · 2026-06-22

1 · The decision in one line

Confirm happens inline on the existing staged-card review list — not in a dedicated sheet. When the scan finds a twin, the two cards are visually tethered with a hand-drawn bracket and a single calm "Ollie noticed" bar appears between them carrying two buttons: Keep one and Keep both. No new screen, no modal, no interruption of the save rhythm the user already has.

Why inline beats a sheet. The locked scope is "the staged cards before save" and the existing grammar (RecordView) is a vertical scroll of cards you save one-by-one. A modal sheet would (a) add a top-level screen the PRD asked us to avoid, (b) yank the user out of the list they're already reading, and (c) risk feeling like a blocking error. Inline keeps the dominant no-duplicate path literally unchanged (A4) and makes the rare duplicate feel like Ollie leaning in to point at two cards, not a guardrail slamming down. The cards being compared stay on screen, side-by-side in the scroll — so "are these really the same?" is answered by looking, not by trusting a summary.

3 · The full state set

The dedup layer adds one card substate, flaggedDuplicate, that wraps a group of two-or-more review-ready cards. Below is every state the user can land in.

(a) No duplicates

The common case. No bracket, no bar, no badge. Cards save one-by-one exactly as today. A4: zero friction

(b) One duplicate pair

Two cards tethered; one "Ollie noticed" bar between them with Keep one / Keep both. The centerpiece — see §4.

(c) A group of 3+ identical

All N cards tethered under one bracket. Bar reads "3 cards look like the same bill". Keep one expands to a tiny chooser (pick the survivor); Keep all is the one-tap escape. No nested pairs — one group, one decision.

(d-i) Same-photo dupe

Reason chip reads 📷 same photo. High confidence — Ollie is sure. Survivor defaults to the first-staged card (they're pixel-identical, so it doesn't matter which).

(d-ii) Same-details dupe

Reason chip reads ≈ same merchant, amount & date. Lower confidence (could be two real £30 coffees). The bar leads with the softer "maybe the same?" wording and shows the matched fields so the user can judge.

(e) Keep one

User picks the survivor (default pre-selected, see §3.1). The other card animates to a calm "set aside" collapsed strip — not deleted-red — with a 1-tap Undo. Survivor returns to normal review.

(e') Keep both

One tap. Bracket dissolves, both cards return to normal review with their own Save buttons. Nothing is set aside. This is the safe default escape from a false match.

(f) After resolution

The group is gone; resolved cards are ordinary review cards. Saving proceeds normally. A set-aside card stays visible (collapsed, undoable) until the session is saved, then is simply never written.

3.1 · How "keep one" decides the survivor (the default)

"Keep one" must pre-select a sensible survivor so the common path is genuinely one tap — but the choice is always overridable and always visible.

SituationDefault survivorWhy
Same-photo pairFirst-staged cardPixel-identical — the data is the same, so order is the only tiebreak. No real choice to make.
Same-details pair, one richerThe more complete card (has merchant + date + line items; fewer carried gaps)Keep the card that needs no further fixing. A photo card with line items beats a bare typed "taxi 240".
Same-details pair, equal completenessThe photo-sourced card, else first-stagedA photo carries proof (the receipt image) the user may want later.
The survivor is shown with a “keep this one” highlight ring (pine green) and the other with a dimmed "set aside" treatment before the user commits, so picking a different survivor is a single tap on the other card. The amount on the survivor is never touched — it's the same Decimal it always was (A5).

Money-safety reads, made literal. (1) Keep both is the filled pine button on the left — the easy, prominent path; Keep one is the quieter outline. (2) The set-aside card is dimmed grey, badged "SET ASIDE IF KEPT 1", and tagged with an Undo after commit — it is never styled in the destructive red BillOwl uses for real deletes. (3) Both amounts stay on screen in the monospaced money font; the survivor's ¥240 is visibly the same value it always had. (4) Nothing is removed at flag time — removal happens only on the explicit "keep one" tap, and even then it's reversible until the session is saved.

5 · Microcopy — Ollie's voice

Warm, first-person, never alarming. Ollie notices, never accuses. Wording softens for the lower-confidence same-details case and firms up for an exact same-photo match.

MomentString

Deliberately avoided words: duplicate (jargon-y, accusatory), delete / remove / merge (reads as destructive/automatic). Ollie says "the same bill", "set aside", "keep" — human, reversible, calm.

6 · Match tolerances — recommendations for tech

The confirm step is the safety net, so the scan should lean strict (minimize false positives — a missed dupe is recoverable later; a noisy false flag erodes trust). Hand-off recommendations:

SignalRecommendationRationale
Same photoIdentity of the picked PhotosPickerItem asset first (same localIdentifier / asset ID); fall back to a perceptual/diff hash of the downscaled JPEG for the case where the same image is added via two different picks. Treat as high confidence.Asset identity is exact and free. A hash catches re-encodes. Either way it's the same pixels → safe to flag firmly.
MerchantNormalized exact match: trim, case-fold, collapse whitespace, strip trailing punctuation. Not fuzzy/substring in v1."Taxi" vs "taxi " should match; fuzzy matching ("MK Taxi" vs "Taxi") risks false flags — confirm can't fully rescue a noisy scan.
AmountExact equality on the Decimal (same currency). No tolerance band.Money is exact in BillOwl; "close" amounts are genuinely different bills.
DateSame calendar day in the journal's locale. A card with no date does not match on the date signal (it can still match by photo).Receipts photographed/typed for the same outing share a day; time-of-day is noise.
CombinationFlag when (same-photo) OR (merchant AND amount AND date all match). All three required for the details path.Matches the locked rule; "all three" keeps the details path strict so two real ¥30 coffees at different shops never flag.
When to scanRun the pairwise scan whenever a card enters review (and re-run if an edit changes merchant/amount/date). Operates on the in-memory staged set only — instant on a handful of cards.Keeps detection live as the user edits, with no perceptible delay (PRD perf constraint).
Edge: a card still clarifying or missing its amount is not eligible for a details-match (you can't compare a gap). It can still match by photo. This avoids flagging two half-read cards as "the same".

7 · PRD ambiguities & assumptions

  • Groups of 3+ rendering (PRD open Q). Assumed: one bracket over all N cards, one decision — keep one (with a survivor chooser) or keep all. Not nested pairwise prompts. Lighter and avoids a combinatorial mess.
  • "Keep one" survivor default (unspecified). Assumed the rules in §3.1 (photo→first; details→more-complete, then photo-sourced). Always overridable with one tap before commit.
  • Reversibility after "keep one" (unspecified). Assumed a set-aside card stays visible + Undo-able until the session is saved (then simply never written) — strengthens A5's "explicit tap" with a safety net, no new persistence.
  • Same-details confidence wording (PRD treats both matches the same). Assumed two confidence tiers in copy only (photo = firm, details = tentative "might be"); the action set is identical. No behavioral change, just tone — keeps false-flag trust intact.
  • Whether the matched-fields reason must be shown (unspecified). Assumed yes — a small reason chip ("≈ same merchant, amount & date" / "📷 same photo") so the user can judge, satisfying the "show why they matched" intent without a separate detail view.
