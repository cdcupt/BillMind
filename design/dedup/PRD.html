Duplicate-record detection in a capture session

When a user submits several photos/notes at once, the same bill can land twice. Catch it before save — and let the user decide. · v1 · 2026-06-22

1 · Problem

BillOwl lets a user capture several bills in one Record session — drop a stack of receipt photos, type a few notes, mix both. Each input is recognized into its own staged card, then the user saves them all. But people re-submit the same bill: they photograph a receipt twice, or type a bill they also snapped. Today every card is saved as a separate bill, so the trip total is silently inflated and the ledger gets messy — and the user only notices later, if at all.

2 · Users & the moment

The batch capturer

Back at the hotel after a day out, dumping a handful of receipts into the Record tab at once. Most likely to double-add.

The belt-and-suspenders user

Types “taxi 240” and photographs the taxi receipt to be safe — now it’s two cards for one ride.

The fat-finger

Taps a photo into the session twice without noticing.

3 · Goal

Before the user saves a multi-input session, detect cards that look like the same bill and let the user resolve each pair (keep one or keep both) — so no accidental double-counting, and nothing is ever removed without an explicit tap. Sessions with no duplicates feel exactly as they do today (no new friction).

4 · Locked decisions (PM)

Match rule

Same photo OR same details. Flag a pair when it’s literally the same image, or when merchant + amount + date match. (Exact matching tolerances are a design/tech detail — the confirm step is the safety net against over-matching.)

Action

Flag & confirm — never silent. Surface “these look like the same bill — keep one / keep both.” Consistent with BillOwl’s never-guess-money principle.

Scope

Current session only. Compare the cards staged in this capture session, before save. Does not touch already-saved bills, other sessions, or other devices.

5 · Scope

IN

  • Duplicate detection across staged cards in one Record session, run before save.
  • A confirm interaction (keep one / keep both) for each detected duplicate group.
  • The match logic: same source photo, or matching merchant + amount + date.
  • Client-side (the staged session lives in the app).

OUT (v1)

  • Dedup against already-saved bills in the trip.
  • Cross-session or cross-device duplicate detection.
  • Auto-merge / silent removal.
  • Server-side dedup or any change to the recognition API contract (unless tech finds it necessary — escalate if so).

6 · Success criteria (acceptance)

#GivenThen
A1The same photo is submitted twice in one sessionThe pair is flagged as a duplicate; user can keep one with one tap
A2A typed bill and a photo of the same bill (merchant+amount+date match) are stagedThe pair is flagged; user resolves it
A3Two genuinely distinct bills with identical details (e.g. two £30 coffees, same shop, same day)They may be flagged, but “keep both” is one tap; nothing is auto-removed
A4A session with no duplicatesNo prompt, no added friction — saves exactly as today
A5Any duplicate resolutionA bill is only ever dropped after an explicit user tap; the kept bill’s amount is never altered

7 · Constraints

  • Money safety first — never silently drop or merge money; the kept card’s amount/fields are untouched.
  • Fits the existing Record tab / staged-card session flow and the sketch theme; no new top-level screens unless design justifies it.
  • iOS (SwiftUI). Server/API changes are out of scope unless tech proves them necessary.
  • Performance: detection runs on a handful of staged cards — must be instant, no perceptible delay before the confirm/save step.

8 · Open questions for design / tech

  • Exact match tolerances: merchant string (exact vs normalized/case-insensitive?), amount (exact?), date (same calendar day?). Lean strict to minimize false positives, since confirm catches the rest.
  • Same-photo detection mechanism (image hash vs identity of the picked asset).
  • Confirm UX shape: inline on the review list vs a dedicated sheet; how groups of 3+ are shown.
