BillOwl · Product Requirements · Smart Multi-Input Capture (F5+)

Smart multi-input capture: fuse · dedup · review

Drop in several photos and notes at once; the agent combines the ones that describe one bill, drops the duplicates, and hands you a clean set to confirm. · v1 · 2026-06-22 · supersedes the narrow "F5 dedup-only" framing

1 · Problem

BillOwl users want to capture a pile of bills at once — drop several receipt photos, type a few notes, mix both — and have the app sort it out. Today the Record tab is incremental and per-card: each input becomes its own card the instant it's entered, and you complete a card by editing its fields. That breaks down in two ways beta users named:

Same bill, twice → two bills

A user photographs a receipt twice, or types a bill they also snapped. Each becomes a separate saved bill → the trip total is silently inflated. (original F5)

One bill, split across inputs → two half-bills

A photo captures only half a bill (amount cut off); the user adds a sentence with the rest. Today the sentence makes a second, separate card instead of completing the photo's bill. (the photo-plus-sentence case)

Both come from the same root: the app processes each input in isolation instead of reasoning over the whole batch.

2 · Goal

Let the user add several inputs in one session and tap Done adding; the agent then fuses inputs that are parts of one bill, flags duplicates that are the same bill twice, and presents a clean, reviewable set. The user confirms (every fuse and every duplicate resolution is visible and reversible), then saves. Sessions with a single clean input stay effortless.

3 · The three pillars

1Fuse partials

Detect when two inputs describe one bill that's split across them (e.g. a photo missing its amount + a sentence that supplies it) and combine them into a single card. The user sees "I combined these two" and can split them back apart.

2Dedup copies

Detect when two inputs are the same bill submitted twice (same photo, or matching merchant+amount+date) and flag the group: keep one / keep both. (The committed F5 dedup design is the basis here.)

3Batch review

A "Done adding → Review" step holds inputs so the agent can reason over them together (fusion needs this), then shows the clean set for one confirm-and-save.

4 · Locked decisions (PM)

Money rule

Agent proposes, user disposes. No silent merge or drop; a fuse never invents or changes an amount. Every join/drop is visible and one-tap reversible until Save.

Dedup match (carried from F5)

Same photo OR (merchant + amount + date). Action = flag & confirm, keep one / keep both. Never silent.

Scope of comparison

Within the current capture session only — the batch of inputs added before this Save. Not against already-saved bills, other sessions, or other devices.

The "done" signal

A UI control ("Done adding"), never a parsed trigger word — a magic word is undiscoverable and collides with real bill text.

Open for design/tech to propose (not pre-decided): whether fusion is agent-automatic (it guesses the photo and sentence go together) or user-directed (the user attaches a note to a specific card), or a blend (agent proposes, user confirms). Lean toward "agent proposes a fuse, user confirms/splits," consistent with the money rule.

5 · Scope

IN (v1)

  • A batch capture session with a Done-adding → Review step.
  • Fusion of inputs that complete one bill (at minimum: a partial photo + a completing text note), proposed by the agent and confirmed by the user (splittable).
  • Dedup per the committed F5 design (same photo OR merchant+amount+date → keep one / keep both).
  • A review surface showing the untangled clean set, with every fuse/dedup action visible + reversible, then a single Save.

OUT (v1)

  • Fusing more than the basic partial-photo + text case (e.g. stitching two photo fragments) — defer unless cheap.
  • Dedup/fuse against already-saved bills, or across sessions/devices.
  • Any silent/automatic merge or drop without user confirmation.
  • Removing the existing quick single-capture path (a lone input must still be effortless).

6 · Success criteria (acceptance)

7 · Constraints

  • Money safety first — the kept/fused card's amount is always traceable to a real input; the agent never fabricates a number to "complete" a bill (if the amount is still missing after fusion, the card is flagged "amount required," as today).
  • Fits the Record tab + sketch theme; the single-input fast path stays.
  • iOS (SwiftUI) client; the agent reasoning may need a server change (batch endpoint) — tech to determine; that's allowed for this feature (unlike the narrow F5).
  • Capture stays AI-first; local fallback only when offline/pre-sync (existing principle).

8 · Open questions for design / tech

  • Fusion trigger: agent-automatic vs user-directed vs propose-and-confirm (lean: propose-and-confirm).
  • Where fusion + dedup run: client over recognized cards, or a server batch step (the agent already lives server-side) — tech decides; may need a new endpoint.
  • Review-surface shape: extend the staged-card list, or a dedicated review screen for the batch.
  • How a fused card shows its provenance (photo + the note that completed it) and how "split" works.
  • Match/fuse tolerances (carry F5's: merchant normalized-exact, amount exact, date same-day; same-photo via asset id + perceptual hash).
